# SHOP

## PURPOSE

상점 / 장바구니 / 구매 / 상점 재고 / 재입고의 기획과 미결정 사항을 관리한다.

* 실제 구현 완료 상태는 [DONE.md](../DONE.md)를 기준으로 확인한다.
* 다음 영업일에 재입고를 호출하는 시점은 [DAY.md](DAY.md) / 인벤토리 적재 규칙은 [INVENTORY.md](INVENTORY.md)를 따른다.

## CONTENTS

상점 시스템 내부 목차

* 구매 흐름
* 상품 데이터와 런타임 상태
* 장바구니와 구매 확정 책임
* 상점 목록 / 상세 / 장바구니 UI
* 카테고리와 정렬
* 상점 재고와 재입고
* 오브젝트 풀링
* 미구현 / 미결정

## CONFIRMED

확정 규칙

### 구매 흐름

* 구매 흐름은 상품 선택 -> 장바구니 확인 -> 구매 확정 순서로 진행한다.
* 상품 선택 단계에서는 자금을 차감하지 않고 구매 확정 시 현재 자금 / 상점 재고 / 인벤토리 수용 가능 여부를 다시 검증한다.
* 구매 성공 시 상점 재고 차감 / 인벤토리 증가 / 자금 차감 / 장바구니 초기화를 하나의 결과로 처리하며 상품은 배송 대기 없이 즉시 들어온다.
* 검증 하나라도 실패하면 전체 구매를 실패 처리하고 부분 구매와 부분 상태 변경은 허용하지 않는다.
* 현재 1차 구현된 판매 상품은 아기 파츠이며 정비 대상 상품의 최초 구매에도 같은 구매 시스템을 재사용한다.
* 정비 대상은 상점에서 최초 단계만 구매하고 상위 단계 구매와 영구 효과 상태는 [UPGRADE.md](UPGRADE.md)가 담당한다.
* 상점의 시설 분류는 배치 가능한 `장비 / 가구 / 시설 확장` 상품군이며 정비 화면의 시설 성장 분류와 구분한다.
* 연구 정비 상품의 상점 분류는 장비이며 최초 1회 구매 후 상점에서 다시 구매하지 않고 상위 단계는 정비 화면에서 올린다.
* 시설 확장은 창고 / 선반처럼 필요에 따라 계속 추가 구매하는 상품이며 정비 상품의 영구 소유·재구매 차단 규칙을 적용하지 않는다.
* 가구는 배치 상태에 따라 평가에 소폭 영향을 주는 상품군으로 사용하며 정확한 계산 규칙은 해당 시스템 구현 전에 확정한다.

### 상품 데이터와 런타임 상태

* 판매 상품군의 공통 데이터 부모는 PurchasableData이며 상품 ID / 이름 / 설명 / 기본 가격 / 기본 최대 재고 / 기본 재입고 간격 / 상점 아이콘 / 상품군을 관리한다.
* PartsData는 PurchasableData를 상속하고 PartType / CraftCost / Themes를 관리하며 세부 파츠 데이터는 PartsData를 상속한다.
* IPurchasable은 데이터 맵 저장 타입이나 Inspector 목록 구성에 사용하지 않는다.
* PurchasableDataMap은 PurchasableData 목록 하나를 보유하고 상품군 또는 PartType으로 분류하며 타입별 개별 배열은 사용하지 않는다.
* ScriptableObject에는 현재 가격 / 남은 재고 / 해금 상태 / 장바구니 수량 같은 런타임 변경값을 저장하지 않는다.
* 상품 데이터에는 주문별 요구 상태 / 제작 배치 상태 / 정비 소유 단계처럼 담당 Model이 보관하는 런타임 상태를 중복 저장하지 않는다.
* 소모품 데이터는 `PurchasableData`를 상속하고 현재 3종에 필요한 효과 종류 하나와 효과값 하나만 추가한다. 효과 적용 규칙 / 선택 주문 / 소비 상태 / 배송 결과는 저장하지 않으며 [DELIVERY.md](DELIVERY.md)가 담당한다.
* 소모품 효과 종류는 주문 대금 보정 / 지연 배송 배율 변경 / 주요 요구 미달성 지급 상한 변경만 우선 지원하고 지속 시간 / 중첩 / 범용 대상 필드는 추가하지 않는다.
* ShopItem은 현재 가격 / 최대 재고 / 남은 재고 / 재입고 간격 / 해금 상태를 보관하고 품절은 남은 재고가 0 이하인지 계산한다.
* 현재 판매 가격은 ShopItem.CurrentPrice를 단일 원본으로 사용한다.
* CartItem은 상품과 수량만 보유하고 가격 / 소계 / 총액은 저장하지 않는다.
* 화폐와 가격 계산은 float를 사용하고 UI에서는 소수점 아래를 표시하지 않지만 검증과 차감에는 원본 값을 사용한다.

### MVP 책임

* ShopModel은 상품 ID별 ShopItemModel을 보관하고 상품 조회 / 필터 / 정렬 / 상점 상태 변경을 담당한다.
* CartModel은 상품 추가 / 동일 상품 수량 누적 / 수량 변경 / 제거 / 전체 초기화 / 입력 검증을 담당한다.
* PurchaseModel은 CartModel / ShopModel / InventoryModel / PlayStateModel을 이용해 구매 사전 검증과 전체 상태 변경을 처리한다.
* ShopPresenter는 View 이벤트 수신 / Model 호출 순서 / ViewData 변환 / ShopView 갱신만 담당한다.
* ShopView는 판매 목록 / 공용 상세 패널 / 장바구니 목록과 장바구니 버튼의 현재 수량을 표시하고 입력 이벤트만 전달한다. 수량 표시는 사용자 Play Mode에서 확인했다.
* TopBar 자금은 PlayStateModel 변경 이벤트를 구독하는 TopBarPresenter가 갱신하며 ShopPresenter가 직접 갱신하지 않는다.
* 구매 결과는 최소한 Success / CartEmpty / ProductNotFound / InvalidQuantity / OutOfStock / NotEnoughBudget / InventoryFull을 구분한다.

### 상점 UI

* 판매 슬롯은 아이콘 / 이름 / 현재 가격 / 남은 재고 / 품절·잠금 상태를 표시하고 상품 ID 선택 이벤트를 전달한다.
* 품절 상품은 회색 처리하되 슬롯 선택과 공용 상세 진입을 허용하고 구매 대신 빠른 재입고 가능 여부를 안내한다.
* 잠긴 일반 상품은 상점 목록에서 제외해 현재 구매 가능한 상품을 우선 표시하고, 정비 시스템 최초 진입에 필요한 시설 상품만 잠금 상태로 계속 표시한다. 잠긴 시설 상품은 구매 / 장바구니 추가 / 빠른 재입고를 허용하지 않는다.
* 상품 상세 패널은 상품별로 만들지 않고 공용 패널 하나를 사용한다.
* 상세 패널의 초기 수량은 1이며 수량 입력 / 증감 / MIN / MAX로 이번에 추가할 수량을 정한다.
* MIN은 1 / MAX는 남은 상점 재고에서 기존 장바구니 수량을 뺀 추가 가능 수량이다.
* 확인 입력은 선택 수량을 기존 장바구니 수량에 누적하고 취소 또는 패널 닫기는 반영하지 않는다.
* 상세 패널을 다시 열면 임시 선택 수량을 1로 초기화한다.
* 장바구니 슬롯은 아이콘 / 이름 / 수량 / 현재 가격 / 소계 / 수량 증감 / 수량 입력 / 삭제를 제공한다.
* 장바구니 상품 이름이 표시 영역을 넘으면 말줄임표로 표시한다.
* 장바구니 수량 입력 0과 삭제 버튼은 항목 제거로 처리한다.
* 잘못된 문자열 / 음수 / 허용 범위 초과는 Model이 거부하고 View는 기존 유효 수량으로 복구한다.
* 장바구니 예상 잔액은 현재 자금 - 현재 장바구니 총액이며 음수도 표시하고 실제 구매 가능 여부는 구매 확정 시 판단한다.

### 오브젝트 풀링

* 상점 상품 슬롯은 `GameManager`가 소유한 공용 `PoolManager`와 Unity `ObjectPool`을 사용하고 슬롯 프리팹을 풀 구분 기준으로 삼는다.
* 상품 ID별 전용 풀이나 전용 인스턴스를 만들지 않으며 최대 생성 수는 한 번에 표시한 상품 수에 수렴한다.
* 품절 상품은 목록에서 제거하지 않고 기존 슬롯의 품절 상태만 갱신한다.
* 목록을 다시 만들 때 활성 슬롯을 풀로 반환하고 재사용 시 상품 ID / ViewData / 선택 이벤트 / 형제 순서를 다시 설정한다.
* 반환 전 선택 이벤트 / 상품 ID / 선택 상태 / Tween / 크기 / 투명도를 초기화하며 등장 연출은 같은 인스턴스에서 최초 한 번만 실행한다.

### 카테고리와 정렬

* 전체 / 파츠 / 시설 / 소모품은 메인 카테고리 Button / 세부 분류와 정렬은 공용 TMP_Dropdown을 사용한다.
* 파츠는 전체 / Body / Eye / Nose / Mouth / Arms / Legs / Hair / Wings / Tail / Claws / Horns를 제공한다.
* 시설은 전체 / 장비 / 가구 / 시설 확장을 제공하고 가구는 시설에 임시 편입한다.
* 소모품은 현재 전체만 제공하고 세부 타입이 생기면 확장한다.
* 정렬은 기본 / 이름 오름차순 / 이름 내림차순 / 가격 낮은 순 / 가격 높은 순을 제공한다.
* 메인 카테고리 버튼을 누르면 공용 분류 옵션을 교체하고 0번 전체 항목으로 초기화해 목록을 즉시 갱신하며 같은 버튼을 다시 눌러도 해당 카테고리 전체로 돌아간다.
* 전체와 소모품은 현재 세부 분류가 하나뿐이므로 공용 분류를 표시하되 입력을 비활성화한다.
* 카테고리 변경 시 정렬을 유지하고 정렬 변경 시 카테고리를 유지한다.
* 상점 재진입 시 전체 카테고리 / 전체 분류 / 기본 정렬로 초기화한다.

### 재입고

* 기본 재입고 주기는 인게임 7일이다.
* 재입고 호출 시점은 [DAY.md](DAY.md)의 다음 영업일 전환 순서를 따르고, 호출됐을 때 조건을 만족한 상품의 남은 재고를 현재 최대 재고까지 복구한다.
* 기본 재입고 간격과 이벤트 / 업그레이드가 반영된 현재 간격을 분리한다.
* 일반 재입고는 다음 영업일의 `TotalDay`를 기준으로 `RestockSpan > 0`이고 `(TotalDay - 1) % RestockSpan == 0`인 상품만 현재 최대 재고까지 채운다.
* `RestockSpan`이 0 이하인 상품은 일반 자동 재입고 대상에서 제외한다.
* 전체 상품 즉시 재입고 함수는 이벤트 / 정비 / 수동 처리 확장에 사용할 수 있도록 유지하되 다음 영업일 자동 재입고에서는 사용하지 않는다.
* 제작에 필요한 파츠가 부족할 때는 선택한 상품 하나에 자금을 지불해 빠른 재입고를 실행할 수 있으며 일반 재입고 주기와 별도로 처리한다.
* 빠른 재입고는 선택 상품을 현재 최대 재고까지 채우고 이용료는 해당 상품 기본 단일 가격의 1.5배를 1차 테스트값으로 사용한다.
* 빠른 재입고 이용료와 재입고 후 실제 상품 구매 비용은 별도로 지불한다.
* 빠른 재입고는 전체 상품을 합해 하루 최대 3회까지 사용할 수 있고 다음 영업일에 사용 횟수를 초기화한다.
* 빠른 재입고는 해당 상품의 일반 재입고 예정일을 변경하지 않는다.
* 임프 심부름꾼을 고용하면 기존 빠른 재입고 비용 계산에 0.75 배율을 한 번 적용한다.
* 현실 시간 / 오프라인 진행 / 기기 시간 기준 재입고는 보류한다.

### 정비 상품 최초 구매

* 상점은 정비 상품의 최초 구매만 처리하고 구매 성공 후 해당 정비 항목의 소유와 1단계 적용을 요청한다.
* 이미 소유한 정비 상품은 다시 구매할 수 없으며 상위 단계는 정비 화면에서만 구매한다.
* 위 재구매 차단은 `MaintenanceData`인 정비 상품에만 적용하며 반복 구매 상품인 시설 확장에는 적용하지 않는다.
* `MaintenanceData`가 `PurchasableData`를 직접 상속하므로 별도 연결용 상품 클래스를 추가하지 않고 같은 데이터의 상품 ID / 정비 종류 / 단계 데이터를 기존 `PurchasableDataMap`과 `MaintenanceModel`이 각 책임에 맞게 사용한다.
* 정비의 실제 효과 / 단계 / 비용 / 선행 조건은 `MaintenanceData`와 단계 데이터가 원본이며 상점 전용 데이터에 복제하지 않는다.
* 정비 상품 최초 구매도 기존 자금 / 상점 재고 / 중복 소유 / 효과 적용 가능 여부를 사전 검증하고 실패 시 부분 상태 변경을 남기지 않는다.
* 파츠 최대 재고 정비는 아기 파츠 상품에만 적용하고 현재 재고를 무료로 채우지 않는다.
* 일반 재입고 간격 정비는 다음 일반 재입고 이후 새 주기부터 적용하고 최소 3일을 보장한다.
* 잠긴 파츠의 해금 정보는 카탈로그와 연구 화면에서 확인하며 상점 목록에서는 제외한다. 시설 상품만 정비 최초 구매 진입을 위해 잠금 상태 표시를 유지한다.

## DATA_BALANCE

실제 파츠 데이터 작성에 사용할 1차 확정 기준이다. 플레이 테스트 결과에 따라 수치는 다시 조정할 수 있다.

### 파츠 가격과 최소 제작 원가

* `BasePrice`는 경제 가치 / `CraftCost`는 제작 예산을 차지하는 복잡도로 보고 자동 비례시키지 않는다.
* 가격 티어는 저가 `40~60G` / 일반 `70~100G` / 고가 `110~150G` / 특수 `160~200G`를 1차 범위로 사용한다.
* Body + Eye + Nose + Mouth 최소 구성 평균 원가는 약 `300G` / 목표 범위는 `250~350G`로 둔다.
* PartType별 가격 범위는 Body `90~150G` / Eye `50~90G` / Nose `40~70G` / Mouth `50~80G` / Arms와 Legs `40~80G` / Hair와 Tail `60~110G` / Wings `90~150G` / Claws `60~100G` / Horns `80~140G`를 후보로 사용한다.
* 연구 파츠라는 이유만으로 자동 고가 처리하지 않고 주문 대금을 직접 올리지 않는 장식성 파츠는 과도하게 비싸지 않게 조정한다.
* 초기 대표 파츠에는 특수 `160~200G` 티어를 사용하지 않고 실질 상한을 `140~150G`로 둔다.

### 파츠 재고와 재입고

* PartType별 기본 재고는 Eye / Arms / Legs `7~9` / Nose / Mouth `6~8` / Body / Hair / Tail / Claws `4~6` / Wings / Horns `4~5`를 기준으로 하며 연구 파츠도 최소 4개를 권장한다.
* 파츠 기본 재입고 간격은 우선 모두 7일로 통일하고 희소성은 재입고 주기가 아니라 기본 재고 수량으로 구분한다.
* 기존 재입고 정비의 단계당 1일 단축 / 최소 3일 구조는 유지한다.

### 초기 상점과 해금 반영

* Day 1에는 Slime / Imp / Mushroom의 Body / Eye / Nose / Mouth / Arms / Legs 기본 파츠 약 18개만 해금한다.
* 초기 무료 파츠는 지급하지 않으며 각 상품의 현재 재고는 `BaseStockQuantity`로 초기화한다.
* 새 종족의 기본 파츠와 이미 연구 조건을 충족한 확장 파츠는 종족 해금 당일 상점에 즉시 표시한다.
* 새로 해금된 파츠는 이미 생성된 주문을 바꾸지 않고 다음 영업일부터 신규 주문 후보에 포함한다.
