# DELIVERY

## PURPOSE

배송 / 주문 조건 평가 / 등급 / 보상 / 결과 피드백의 기획과 미결정 사항을 관리한다.

* 실제 구현 완료 상태는 [DONE.md](../DONE.md)를 기준으로 확인한다.
* 주문 상태와 기한은 [ORDER.md](ORDER.md) / 제작 판정 입력은 [CRAFT.md](CRAFT.md) / 결산 집계는 [DAY.md](DAY.md)를 따른다.

## CONFIRMED

확정 규칙

* 제작 완료 후 배송 전 주문은 진행 중이며 상태를 배송 대기로 표시한다.
* 배송은 배송 대기 / 출발 / 배송 중 / 도착으로 구분하고 배송 중 주문은 다음 영업일로 이월한다.
* 배송 소요일이 0일이면 출발 직후 같은 날 도착하고 1일 이상이면 확정된 도착 예정일까지 배송 중 상태를 유지한다.
* 직원이 없어도 기본 직접 배송으로 동시에 1건을 출발시킬 수 있고 배송 직원 1명당 동시 배송 가능 수를 1건 늘린다.
* 배송 직원은 동시 배송 수 / 배송 설비는 배송 소요일 단축을 담당해 같은 효과를 중복 소유하지 않는다.
* 플레이어가 배송 화면에서 직원 배송을 선택하면 배치 가능한 배송 직원 한 명을 자동 배정하며 제작 완료 즉시 자동 출발하지 않는다.
* 직원과 설비 효과는 새로 출발하는 배송부터 사용하고 이미 확정된 배송 일정은 변경하지 않는다.
* 배송 출발 전 예상 도착일 / 납품 마감일 / 예상 정상 또는 지연 결과를 확인할 수 있어야 한다.
* 납품 기한 이내 배송은 정상 납품 / 마감 후 지연 허용 기간 내 배송은 지연 납품이다.
* 지연 납품 보상은 정상 보상 계산 결과의 50%를 초기 기본값으로 사용한다.
* 최소 제작 조건은 제작 확정 전에 검사하므로 미충족 제작물은 납품 단계에 도달하지 않는다.
* 주요 요구 미충족 상태로 납품할 수 있으나 평가가 크게 하락하고 희망 충족은 추가 점수를 준다.
* 제작 중 미리보기와 제작 확정은 [CRAFT.md](CRAFT.md)의 동일한 점수 계산 규칙을 사용하고 제작 확정 시 항목별 판정 결과를 고정한다.
* 배송 단계는 주요 요구 / 희망 / 테마를 다시 계산하지 않고 고정된 제작 판정 결과에 정상 / 지연 배송 결과를 반영한다.
* 계산 순서는 제작 판정 결과 고정 -> 배송 출발 -> 배송 도착 -> 배송 결과 반영 -> 평가 등급 -> 최종 보상이다.
* 주문 보상은 평가 결과에 따라 달라지고 상점 현재 판매 가격과 직접 연결하지 않는다.
* 보상은 PlayStateModel 자금 변경을 통해 지급하고 TopBarPresenter가 자금 변경 이벤트로 화면을 갱신한다.
* 제작 완료 주문은 주문 상세를 거치지 않고 배송 화면으로 바로 이동하며 제작 완료 패널의 배송 입력도 같은 흐름을 사용한다.
* 배송 출발 후 배송 패널을 닫고 배송 중 주문은 진행 중 탭에서 읽기 전용 배송 정보를 표시한다.
* 도착 완료 주문은 종료 탭에서 확정 배송 결과를 읽기 전용으로 표시한다.
* 확정 배송 결과는 내부 원본을 직접 노출하지 않고 복사본으로 저장하고 조회한다.

### 배송 방식 선택과 직원 배치

* 배송 방식은 기본 직접 배송과 직원 배송으로 구분한다.
* 기본 직접 배송 슬롯은 1개이며 사용 중이면 다른 주문의 직접 배송 출발을 차단한다.
* 기본 직접 배송은 직원 배치 없이 사용하는 대신 `DeliverySettingData`의 건당 30G 고정 배송비를 출발 성공 시 한 번 지출하고 일일·주간 결산의 직접 배송비 항목에 기록한다. 직원 배송은 건당 배송비 없이 주급만 지출한다.
* 배송 대기 화면을 열 때마다 직접 배송 / 직원 배송 선택을 모두 초기화하고, 플레이어가 사용 가능한 방식 하나를 직접 선택한 뒤에만 출발할 수 있다.
* 직원 배송을 선택하면 배치 가능한 고용 직원 중 한 명을 자동 배정하고 배치 가능한 직원이 없으면 직원 배송 토글과 출발을 비활성화한다.
* 배송 일정과 확정 결과에는 배송 방식 / 직원 ID를 보존해 배송 중과 완료 화면에서도 같은 담당 정보를 표시한다.
* 직원 배송 출발 전에 주문 / 일정 / 직접 배송 슬롯 또는 직원 고용·배치 상태를 모두 검증하고 주문 상태 변경 실패 시 직원 배치와 배송 일정을 원상 복구한다.
* 배송 도착이 정상 완료된 뒤 해당 직원 배치를 한 번만 해제하며 0일 배송도 출발 배치와 즉시 해제를 각각 한 번만 처리한다.
* 배치 중인 직원 카드는 해고할 수 없고 배송 완료 후 다시 고용 탭에서 배송 가능 상태로 표시한다.

#### 제작일과 배송일 예시

* 3월 2일 제작 완료 / 3월 3일 배송 출발 / 3월 5일 도착이면 각 날짜 결산에 제작 완료·배송 대기 / 배송 출발 / 도착·납품·주문 수익을 기록하고 도착과 기한 실패가 겹치면 도착 배송을 먼저 처리한다.

### 특수 테마 보정

* 목표 테마 특수 주문은 목표 테마가 활성화되면 일반 주문보다 해당 테마 점수를 높게 적용한다.
* 목표가 아닌 동시 활성 테마는 일반 점수를 적용한다.
* 목표 테마 보정 / 일반 테마 감쇠 / 상한 / 상극의 계산 순서와 프로토타입 수치는 [CRAFT.md](CRAFT.md)를 따른다.

### 평가 피드백

* 평가 화면은 최소 제작 조건 / 주요 요구 / 희망 / 활성 테마 / 완성 테마 / 상극 충돌 / 배송 결과를 아이콘과 짧은 문구로 구분한다.
* 예: 최소 조건 충족은 체크 / 주요 요구 미충족은 X / 상극 발생은 경고 아이콘으로 표시한다.
* 세부 항목에서 어떤 조건이 성공 / 실패 / 감점되었는지 확인할 수 있게 한다.
* 평가 Model이 결과와 실패 원인을 계산하고 Presenter가 ViewData로 변환하며 View는 아이콘 / 문구 / 점수만 표시한다.

## PROTOTYPE_BALANCE

배송 1차 구현과 플레이 테스트에 사용할 초기 기준이며 최종 밸런스 확정값이 아니다. 수치는 `DeliverySettingData`에서 조정할 수 있게 한다.

### 등급 산정

* 난이도별 주요 요구와 희망 개수가 달라 같은 절대 점수 구간을 사용하지 않고 주문별 기준점수 달성률로 등급을 정한다.
* 주문 기준점수는 `조립 완성 점수 + 주요 요구 개수 × 주요 요구 충족 점수 + 희망 개수 × 희망 충족 점수`이다.
* 현재 제작 점수 기준으로는 `100 + 주요 요구 개수 × 100 + 희망 개수 × 40`이다.
* 테마 점수는 기준점수에 포함하지 않고 조건을 충족한 뒤 더 높은 등급을 노리는 보너스로 사용한다.
* 달성률은 `최종 제작 점수 / 주문 기준점수 × 100`으로 계산한다.

| 등급 | 1차 달성률 기준 |
| --- | ---: |
| S | 110% 이상 |
| A | 95% 이상 |
| B | 70% 이상 |
| C | 40% 이상 |
| D | 40% 미만 |

* B등급 이상이면 PlayStateModel의 고등급 평가 누적 수를 한 번 증가시킨다.

### 보상 기준 원가

* 기본 주문 대금은 몸통 / 눈 / 코 / 입 최소 구성과 모든 주요 요구의 기준 가격에 실제 달성한 희망 사항의 기준 가격을 더해 계산한다.
* 같은 파츠가 최소 구성과 주요 요구 / 희망을 함께 해결하면 한 번만 계산하고 가장 큰 필요 수량을 적용한다.
* 사용 파츠 기본 가격 합계는 제작에 실제 사용한 모든 파츠의 `BasePrice` 합계이며 기본 주문 대금과 별도로 기록한다.
* 주문과 무관한 추가 파츠는 사용 파츠 기본 가격 합계만 증가하고 기본 주문 대금을 올리지 않는다.
* 기본 주문 대금과 사용 파츠 기본 가격 합계는 상점의 현재 판매 가격과 직접 연결하지 않고 파츠 `BasePrice`를 사용한다.

### 보상 배율과 계산 순서

| 난이도 | 1차 난이도 보정 |
| --- | ---: |
| Easy | 1.2 |
| Normal | 1.3 |
| Hard | 1.4 |

| 등급 | 1차 등급 배율 |
| --- | ---: |
| S | 1.5 |
| A | 1.25 |
| B | 1.0 |
| C | 0.7 |
| D | 0.3 |

* VIP 배율은 1.5 / 일반 주문 배율은 1.0을 초기값으로 사용한다.
* 정상 배송 배율은 1.0 / 지연 배송 배율은 0.5를 초기값으로 사용한다.
* 주문 대금 원값은 `기본 주문 대금 × 난이도 보정 × 등급 배율 × VIP 배율 × 배송 배율` 순서로 계산하고 소모품 보정과 주요 요구 미달성 상한까지 적용한 뒤 최종 10단위 처리를 한 번만 수행한다.
* 주요 요구를 하나라도 달성하지 못하면 주문 대금 원값을 사용 파츠 기본 가격 합계의 80% 이하로 제한해 최소 조립만 맞춘 납품으로 이익을 얻을 수 없게 한다. 상한이 적용된 결과는 10단위 내림 / 상한이 적용되지 않은 결과는 10단위 일반 반올림한다.
* VIP와 배송 보정을 제외한 일반 주문 정상 배송 기준으로 B등급 이상은 흑자 / C등급은 손익분기 이하 / D등급은 명확한 손실이 나도록 테스트하고 VIP가 낮은 등급의 손실을 과도하게 상쇄하는지도 함께 확인한다.

### 배송 소모품 1차 확정안

* 포장 상자 / 포장재 / 완충제 3종은 제작 완료 후 배송 출발 전에 선택하고 한 주문당 한 종류만 1개 사용할 수 있으며 선택하지 않고도 배송할 수 있다.
* 선택한 소모품은 배송 출발이 확정될 때 1개 소비하고 서로 중첩하지 않으며 배송 등급 자체를 직접 올리지 않는다.
* 포장 상자 30G는 기존 최종 주문 대금에 +5% / 포장재 60G는 지연 배송 배율을 `0.5 -> 0.65` / 완충제 20G는 주요 요구 미달성 지급 상한을 `80% -> 90%`로 완화한다.
* 포장재는 정상 배송에 영향을 주지 않고 완충제는 주요 요구 미달성 판정이나 패널티 자체를 제거하지 않는다.
* 소모품 보정은 기존 배송 대금 계산이 소유한다. 포장재의 지연 배율 -> 기본 대금 / 난이도 / 등급 / VIP / 배송 배율 -> 포장 상자 +5% -> 주요 요구 미달성 시 기본 80% 또는 완충제 90% 상한 -> 최종 10단위 처리 순서로 계산해 포장 상자가 미달성 상한을 넘기지 않게 한다.
* 배송 출발 성공 시 선택한 소모품 ID를 배송 일정과 확정 결과에 보존하고 계산된 최종 보상값과 함께 저장한다. 복구 후에는 소모품 효과를 다시 계산하지 않고 저장된 확정 결과를 사용한다.

#### 보상 계산 예시

* 기본 주문 대금이 600G인 주문이 Normal / A / VIP / 정상 배송이면 `600 × 1.3 × 1.25 × 1.5 × 1.0 = 1,462.5`이므로 최종 주문 대금은 1,460G이다.
* 사용 파츠 기본 가격 합계가 500G이면 기준 이익은 `1,460 - 500 = 960G`이며 이익 계산과 기록은 결산 시스템에서 담당한다.
* 달성하지 않은 희망과 주문에 필요하지 않은 추가 파츠의 가격은 기본 주문 대금을 올리지 않는다.

### 배송 결과 UI

* `DeliveryView`는 배송 전 예상 결과 / 배송 중 정보 / 도착 후 확정 결과를 같은 패널에서 상태별로 표시한다.
* 배송 전에는 정상·지연 예정 / 예상 등급 / 예상 주문 대금 / 현재 점수와 기준점수 / 적용 배율 / 납품 기한을 우선 표시한다.
* 주요 요구 / 희망 / 활성 테마 결과는 제작 평가 요약에서 확인하고 기본 주문 대금 / 난이도·등급·배송·VIP 보정 / 예상 주문 대금은 보상 내역에서 확인한다.
* 제작 결과 구역은 제작 점수 / 예상 등급 / 정상 또는 지연 배송 결과를 표시하며 예상 점수 항목을 별도로 반복하지 않는다.
* 제작 상세 구역은 주요 요구와 희망 진행 슬롯 / 활성 테마 고정 슬롯을 사용하고 진행 슬롯은 달성 개수 Text와 진행 바만 갱신한다. 테마 슬롯은 실제 활성 개수만큼 표시한다.
* 보상 내역 구역은 기본 보상 / 등급 보정 / 배송 보정 / 특수 주문 보정 / 최종 예상 보상을 표시한다. 상단 제목 구역의 예상 보상 Text는 제거해 같은 값을 중복 표시하지 않는다.
* 보정 문구는 종류와 배율 또는 금액을 함께 표시하고 특수 주문 보정의 `/` 뒤 상세 문구는 줄바꿈해 자동 글자 크기가 과도하게 작아지지 않게 한다.
* 배송 전 행동은 배송 출발 / 돌아가기를 사용하고 배송 중과 도착 결과 화면은 읽기 전용으로 표시한다.
* 정상·지연 배송으로 종료된 주문을 다시 선택하면 일반 주문 상세 대신 확정 배송 결과를 읽기 전용으로 표시한다.
* 정상은 초록 체크 / 지연은 주황 시계 / 미충족은 빨강 X / 상극은 경고 아이콘처럼 색상과 기호를 함께 사용한다.

## IMPLEMENTATION_FLOW

현재 배송 처리 구조와 순서

* Crafted는 배송 대기 / Shipping은 배송 중 / Closed는 도착 후 종료 상태로 사용한다.
* 배송 소요일은 배송 출발 전에 주문별로 한 번 확정하고 같은 주문의 화면 재진입으로 바뀌지 않게 별도 배송 일정 데이터에 저장한다.
* 배송 예상은 현재 영업일이 아니라 예상 도착일을 기준으로 정상 / 지연 여부와 예상 주문 대금을 계산한다.
* 배송 출발은 주문 상태와 일정을 Shipping으로 변경하고 당일 배송 출발만 기록하며 자금 / 완료 주문 수 / 평가 누적을 변경하지 않는다.
* 소요일이 0일이면 출발 처리 직후 같은 날 도착 처리를 실행하고 1일 이상이면 다음 영업일로 이월한다.
* 영업 종료 시 `DeliveryModel`이 오늘 도착 예정인 Shipping 주문을 먼저 처리하고 그다음 `CustomerOrderModel`이 미도착 주문의 기한과 최종 실패를 판정한다.
* 배송 도착은 확정 제작 결과와 실제 도착일로 배송 결과를 생성하고 주문 종료 / 주문 대금 지급 / 완료 주문 수 / B등급 이상 평가 누적 / 당일 도착 기록을 한 번만 반영한다.
* 주문 목록과 배송 화면은 배송 대기 / 배송 중 / 도착 완료를 구분하고 배송 중에는 출발일 / 도착 예정일을 읽기 전용으로 표시한다.
* 배송 일정과 Shipping 상태 / 출발과 도착 처리 / 영업 종료 연결 / 주문과 배송 UI / 기록과 결산 / 실패 원상 유지까지 1차 구현을 완료했다.
