# SAVE_LOAD

## PURPOSE

저장 / 불러오기 대상과 런타임 데이터 복구 기준의 초기 기획과 미결정 사항을 관리한다.

* 실제 구현 완료 상태는 [DONE.md](../DONE.md)를 기준으로 확인한다.
* 현재 시스템들의 런타임 원본과 타이틀 / Play 저장 UI 구성을 기준으로 저장 구조와 복구 규칙을 관리한다.

## CONTENTS

저장 시스템 내부 목차

* 플레이 상태와 달력
* 주문과 누적 생성 번호
* 제작물과 평가 입력
* 상점 재고와 가격
* 인벤토리 스택
* 결산 / 페널티 기록
* 업그레이드와 해금
* ScriptableObject ID 연결
* 저장 슬롯과 UI 모드
* 자동 / 수동 저장
* 저장 예외 처리
* 미구현 / 미결정

## CONFIRMED

현재 보존이 필요한 데이터

* PlayStateModel의 TotalDay / 현재 자금 / 고등급 평가 누적 / 해금 ID와 이후 확정될 영업 상태.
* 수락 대기 / 진행 중 / 종료 주문과 각 주문의 ID / 누적 생성 번호 / 상태 / 기한 / 생성 당시 설정값.
* 주문에 연결된 제작물이 생기면 사용 파츠 / 제작 코스트 / 평가 입력에 필요한 확정 결과.
* CustomerOrderModel의 전체 주문 기록과 다음 누적 생성 번호 / OrderGeneratorModel의 주간 주문량 조정 상태.
* ShopModel의 현재 가격 / 최대 재고 / 남은 재고 / 현재 재입고 간격 / 다음 재입고일 / 대기 중인 재입고 간격. 상품과 파츠 해금은 PlayStateModel을 원본으로 유지한다.
* InventoryModel의 용량과 상품 ID별 총수량. 표시용 스택 / 슬롯 ID / 표시 순서는 저장하지 않고 복구 후 Builder에서 다시 구성한다.
* 일일 / 주간 결산 기록과 가계부에 표시할 과거 주간 기록 / 현재 적용 중인 주문량 페널티.
* 파산 시 현재 주의 시작 시점으로 돌아가기 위한 주간 시작 상태.
* 업그레이드 / 직원 / 파츠 / 특수 주문 / 카탈로그 정보 해금 상태.
* 업적별 현재 단계 / 최종 완료 / 신규 알림 상태와 자동 지급된 해금 / 예약한 장식 ID.
* 타이틀 이어하기에서 복구할 현재 플레이 상태와 엔딩 총 결산에 필요한 누적 확정 기록.
* ScriptableObject 원본을 복제 저장하지 않고 안정적인 ID를 통해 런타임 저장 데이터와 연결한다.

### 현재 구현 범위와 복구 기준

* 최초 저장 스키마 버전은 `1`이며 버전 숫자가 다르다는 이유만으로 불러오기를 차단하지 않는다. 현재 코드가 조회할 수 있는 필드의 값과 참조 관계가 유효한지를 기준으로 복구 가능 여부를 판단한다.
* `SavePathProvider / SaveFileHandler / SaveManager`와 5개 슬롯의 파일 기반을 구현했다.
* PlayState는 누적 영업일 / 현재 자금 / 고등급 평가 누적 / 해금 ID를 저장하고 슬롯 헤더에는 달성 업적 수를 표시한다.
* BusinessDay는 당일 제작 횟수와 최대 횟수 / 빠른 재입고 횟수와 최대 횟수 / 영업 종료 여부를 저장한다.
* Shop은 상품 ID / 현재 가격 / 남은 재고 / 최대 재고 / 재입고 간격 / 다음 재입고일 / 대기 중인 재입고 간격 / 파츠 최대 재고 보너스 / 파츠 재입고 정비값을 저장한다.
* Inventory는 용량과 상품 ID별 총수량만 저장한다. 99개 단위 표시 스택은 복구 후 `InventoryListBuilder`에서 다시 구성한다.
* Order는 생성 시 확정된 주문 정보와 조건 / 진행 상태 / 결과 / 종료일 / 수락 제한 / 페널티를 저장한다. 다음 누적 생성 번호는 CustomerOrderModel, 주간 주문량 조정은 OrderGeneratorModel에서 각각 저장한다.
* Craft는 주문별 확정 배치 파츠 / 루트 몸통 / 제작 조건·테마·점수 판정 결과를 생성 시점의 확정값으로 저장한다.
* Delivery는 배송 소요일 단축값 / 미출발 예상 일정 / 출발·도착일 / 배송 방식 / 담당 직원 ID / 배송비 / 완료 평가와 주문 대금을 저장한다. 완료된 과거 직접 배송은 현재 직접 배송 슬롯 점유 수에서 제외한다.
* 제작과 배송은 현재 런타임 주문을 먼저 변경하지 않고 저장된 Order 데이터를 기준으로 주문 ID와 진행 상태 관계를 사전 검증하며, 전체 검증을 통과한 뒤 실제 Model을 복구한다.
* ScriptableObject 참조는 원본 데이터 전체가 아니라 안정적인 ID로 저장하고 복구 시 DataMap에서 다시 찾는다.
* 업적 / 정비 / 직원처럼 설정 데이터 목록이 확장될 수 있는 시스템은 저장된 항목만 검증·복구하고 저장 이후 새로 추가된 항목은 현재 Model의 초기 상태를 유지한다. 저장된 ID가 현재 DataMap에 없거나 값 범위와 참조 관계가 잘못된 경우에는 `InvalidData`로 차단한다.
* 새로 추가하는 숫자 / bool 저장 필드는 `0 / false`를 정상 초기값으로 사용할 수 있게 설계한다. 다른 초기값이 필요하면 해당 시스템 복구 코드에서 누락 상태를 명시적으로 보완한다.
* 데이터 에셋 ID는 생성 후 변경하지 않는다. 불가피한 ID 변경이 실제로 발생할 때만 해당 ID 변환 범위를 별도로 확정한다.
* 장바구니 / 선택된 슬롯과 상세 / 필터와 정렬 / 스크롤 위치는 저장하지 않는다. 제작 중 배치 임시 상태는 별도 편의 기능이 확정되기 전까지 저장 대상에서 제외한다.
* 제작 결과와 배송 일정·결과 DTO 및 Model 캡처 / 검증 / 복구 진입점을 구현해 `Crafted / Shipping` 주문의 연계 상태를 저장 범위에 포함했다.
* DailyRecord는 현재 일일 기록과 이전 완료 기록 목록을 구분해 저장하며 별도의 현재 기록 완료 여부는 저장하지 않는다.
* Settlement는 가계부 원본인 과거 주간 결산과 구매 상품 / 사용 파츠 / 당시 직원 현황을 저장한다. 가계부는 이 원본을 읽는 화면이므로 별도 저장 데이터를 두지 않는다.
* Maintenance는 정비별 구매 단계와 실제 적용 단계를 저장해 다음 영업일 적용 대기 상태를 두 단계의 차이로 복구한다. 시설 효과의 최종값은 Inventory / Shop / Order / BusinessDay / Delivery 등 실제 담당 Model의 저장 데이터를 원본으로 유지한다.
* Employee는 고용 / 배송 배치 / 미지급 근무일 / 마지막 근무일 / 마지막 주급 지급일을 저장한다.
* Achievement는 업적별 마지막 달성 단계 / 마지막 보상 수령 단계 / 완료 / 신규 알림 상태를 저장한다. 진행도는 일일·주간 원본에서 다시 계산하고 지급된 골드와 해금은 PlayState 및 일일 기록을 원본으로 유지한다.
* Catalog는 파츠 데이터와 PlayState 해금 / Inventory 보유 상태를 읽는 화면이므로 별도 저장 데이터를 두지 않는다.
* 현재 `SaveFileData / SaveFileHandler / PlaySceneSaveHandler`에 위 런타임 상태의 캡처 / 기본 검증 / 시스템 간 참조 검증 / 복구 진입점 연결을 완료했다.
* CustomerOrder / CraftComplete / Delivery / Employee / DailyRecord / Settlement 복구는 각 `SaveRestorer`가 저장 데이터 검증과 런타임 데이터 변환을 담당하고, 각 `RestoreState`가 검증을 마친 상태를 보관하며, 담당 Model은 현재 상태 저장 데이터 생성과 준비된 상태 적용만 담당한다.
* `PlaySceneSaveHandler`는 위 여섯 시스템의 복구 상태를 `PlaySceneRestoreState`에 모두 준비한 뒤 실제 Model 상태를 변경한다. 배송 복구는 현재 런타임 직원 상태가 아니라 먼저 준비한 `EmployeeRestoreState`에서 직원 ID 존재 여부를 확인한다.
* Shop / Inventory / OrderGenerator / Maintenance / Achievement의 복구 검증은 현재 구간이 짧고 각 Model 상태와 직접 연결되므로 별도 `SaveRestorer`로 분리하지 않고 Model에 유지한다.
* Play 설정의 일반 5개 슬롯에서 저장 / 덮어쓰기 / 불러오기 / 삭제를 처리하고, 불러오기 성공 후 열려 있던 화면과 사이드 액션을 정리한 뒤 TopBar와 업적 알림을 복구 상태로 갱신한다.
* 다음 영업일의 날짜 / 정비 효과 / 페널티 / 재입고 / 일일 상태와 기록 / 신규 주문 초기화가 모두 끝난 뒤 현재 활성 슬롯에 자동 저장한다. 활성 슬롯 없이 Play 씬을 직접 실행한 경우에는 자동 저장을 건너뛴다.
* 빈 슬롯 / 정상 슬롯 / 손상 슬롯 / 수동 저장과 덮어쓰기 / 불러오기와 삭제 / 주요 런타임 상태 복구 / 다음 영업일 자동 저장 / 주간 시작 스냅샷과 파산 복구 / 타이틀과 엔딩 연계의 전체 흐름을 사용자 Play Mode에서 확인했다.

### 저장 슬롯과 현재 슬롯

* 저장 슬롯은 5개를 사용한다.
* 슬롯은 `Empty / Valid / Corrupted` 상태를 구분하고 슬롯 번호 / 최근 저장 시각 / 누적 영업일 / 달성 업적 수 / 현재 자금을 목록에 표시한다.
* 새 게임은 슬롯 선택 화면에서 시작한다. 빈 슬롯은 바로 시작하고 기존 정상 슬롯은 덮어쓰기 확인 후 새 게임을 시작한다.
* 기존 저장을 불러오거나 새 게임을 시작한 슬롯은 현재 활성 슬롯으로 유지하며 이후 자동 저장은 해당 슬롯을 덮어쓴다.
* 기존 저장을 덮어쓰는 새 게임은 Play 런타임 초기화와 초기 상태 저장이 성공한 뒤 기존 파일을 교체해 중간 실패로 기존 저장을 잃지 않게 한다.

### 파일 형식과 저장 책임

* 저장 파일은 Unity `JsonUtility`로 변환하는 JSON을 사용하고 최초 저장 버전은 `1`로 시작한다.
* 저장 폴더는 `Application.persistentDataPath/Saves` / 일반 저장 파일은 `save_slot_1.json`부터 `save_slot_5.json` / 주간 시작 스냅샷은 `week_slot_1.json`부터 `week_slot_5.json`을 사용한다.
* 저장 시각은 UTC 기준 문자열로 기록하고 UI에서 표시할 때 현재 환경의 로컬 시각으로 변환한다.
* `SavePathProvider`는 슬롯 번호 검증과 일반 저장 / 주간 스냅샷 / 임시 파일 경로 계산만 담당한다.
* `SaveFileHandler`는 파일 읽기 / 쓰기 / 기본 데이터와 버전 검증 / 삭제를 담당하고 런타임 Model을 직접 참조하지 않는다.
* `SaveManager`는 현재 활성 슬롯 / 5개 슬롯 상태 조회 / 새 게임과 불러오기 슬롯 선택 / 저장 성공 후 슬롯 정보 갱신을 담당하고 시스템별 상태 변환은 담당하지 않는다.
* 저장은 임시 파일 작성과 재읽기 검증이 성공한 뒤 기존 파일을 교체하고 실패하면 기존 정상 파일을 유지한다.

### 자동 / 수동 저장

* 자동 저장은 결산 표시 도중이 아니라 결산 확인과 다음 영업일 초기화가 모두 끝난 안정된 상태에서 실행한다.
* 일반 영업일은 일일 결산 확인과 다음 날 초기화 후, 7일째는 일일·주간 결산 확인과 다음 주 초기화 후 현재 활성 슬롯에 자동 저장한다.
* 결산 화면이 열린 동안에는 Play 설정의 수동 저장에 진입하지 않으며 일일·주간 결산 확인 대기 상태는 저장하지 않는다.
* `1일 / 8일 / 15일...`의 주간 시작 상태는 정상 저장과 별도 스냅샷으로 보관해 파산의 `이번 주부터 다시 시작`에서 사용한다.
* Play 설정 화면의 `저장` 탭은 공용 슬롯 UI를 사용해 수동 저장 / 덮어쓰기 / 불러오기 / 삭제를 제공한다. 타이틀 설정에서는 저장 탭을 표시하지 않는다.
* 수동 저장 화면에서 빈 슬롯의 주 입력은 `저장하기`, 정상 저장 슬롯은 `덮어쓰기`로 표시하고 덮어쓰기 전에 확인한다.

### 공용 슬롯 UI 모드

* 공용 슬롯 View는 `NewGame / Load / Save` 표시 모드를 사용한다.
* Play 설정의 저장 View와 타이틀의 불러오기 View는 같은 슬롯 구조를 재사용하고 상단 DetailBar 문구와 표시 모드만 다르게 설정한다.
* `NewGame` 모드의 빈 슬롯은 `시작하기`, 기존 슬롯은 `덮어쓰기`를 표시한다.
* `Load` 모드의 빈 슬롯은 불러오기를 비활성화하고 정상 슬롯은 `불러오기`를 표시한다.
* `Save` 모드는 저장과 불러오기 버튼을 분리한다. 빈 슬롯은 `저장하기`만 사용할 수 있고 정상 슬롯은 `덮어쓰기 / 불러오기 / 삭제`를 사용할 수 있다.
* 삭제는 사용자가 명시적으로 확인한 슬롯만 처리하며 슬롯 목록 갱신과 실제 파일 처리는 Presenter와 저장 담당 객체를 통해 중재한다.

### 손상된 저장

* 파일 읽기 / 역직렬화 / 유효하지 않은 버전 값 / 필수 데이터 / ScriptableObject ID / 런타임 상태 검증 중 복구할 수 없는 문제가 있으면 해당 슬롯을 `Corrupted`로 표시한다.
* 손상 슬롯은 `손상된 저장 데이터 / 이 저장은 불러올 수 없습니다`를 표시하고 불러오기 입력을 비활성화한다.
* 슬롯 목록의 기본 검증을 통과한 뒤 Play 씬 심층 검증에서 실패한 슬롯도 현재 실행 중 `저장 데이터가 올바르지 않습니다.`를 표시하고 불러오기 입력을 비활성화한다.
* 손상 파일은 자동 삭제하지 않고 그대로 유지하며 사용자가 직접 삭제하거나 새 게임 / 수동 저장에서 확인 후 덮어쓸 수 있다.
* 저장 덮어쓰기는 임시 파일 작성과 검증이 성공한 뒤 기존 파일을 교체해 쓰기 실패 시 이전 정상 저장을 유지한다.

## PENDING

미구현 / 미결정

* 주간 시작 스냅샷 복구 후 정상 저장과 스냅샷을 유지 / 교체하는 세부 규칙 확정.

* 전체 종료 주문과 가계부 과거 주간 기록의 보관 한도 / 파일 크기 정책 확정.
* 설정값을 PlayerPrefs / 별도 설정 파일 / 세이브 데이터 중 어디에 보관할지 확정.
* 저장 중단 / 손상 / 빈 저장 파일별 로그 범위 확정. 복구할 수 없는 저장 데이터의 사용자 안내 문구는 `저장 데이터가 올바르지 않습니다.`를 사용한다.
* 버전 숫자 차이 허용 / 신규 항목 초기 상태 유지 / 알 수 없는 ID 차단 정책은 외부 코드 검토 후 필요한 범위만 추가 보완한다.

## UPDATE_RULE

다른 시스템에서 영구 보존이 필요한 런타임 데이터가 추가될 때 즉시 기록하고 저장 시스템 시작과 종료 시 전체 확인한다.
