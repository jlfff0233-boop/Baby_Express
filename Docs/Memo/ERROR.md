# ERROR

## PURPOSE

개발 진행을 실제로 막았고 원인 추적에 시간이 걸린 오류와 해결 방법을 관리한다.

* 프로젝트 작업 방식과 메모 관리 기준은 [GUIDELINE.md](GUIDELINE.md)에서 관리한다.
* 개발 진행을 막지 않은 경고 / 설계 문제 / 미구현 항목은 기록하지 않는다.
* 실제로 작업이 중단된 오류만 증상 / 원인 / 해결 방법 / 확인 결과와 함께 기록한다.
* 해결된 문제도 같은 증상이 다시 나오면 먼저 이 파일을 확인한다.
* Unity 메타 파일(.meta)은 기록 대상이 아니며 수정하지 않는다.

## ERROR_LIST


### 2026-08-27 결산 중첩 자동 레이아웃 슬롯 겹침

* 증상: 결산 Content 안의 여러 구역에 동적 슬롯을 생성했을 때 각 구역의 슬롯 Text와 아이콘이 한 위치에 겹쳐 표시됐다.
* 원인: 바깥 Content / 구역 / 슬롯 정렬 Content에 자동 레이아웃을 중첩하면서 자식의 높이를 계산할 `LayoutElement`와 `ContentSizeFitter` 책임이 섞였고, 슬롯 생성 후 상위 레이아웃 갱신 순서도 보장되지 않았다.
* 해결: 바깥 Content는 구역 배치, 구역은 타이틀과 슬롯 Content 배치, 안쪽 Content는 슬롯 배치만 담당하도록 나눴다. 슬롯 높이는 `LayoutElement`에서 제공하고 동적 생성 후 안쪽부터 바깥쪽 순서로 레이아웃 크기가 전파되게 구성했다.
* 확인: 일일 결산의 모든 구역과 슬롯이 순서대로 분리되어 표시되는 것을 사용자 Play Mode에서 확인했다.
* 재발 방지: 여러 `VerticalLayoutGroup`을 겹쳐 사용할 때 같은 RectTransform에 위치 정렬과 자기 크기 결정을 동시에 맡기지 않는다. 자식 크기 원본 / 안쪽 Content 크기 확장 / 바깥 구역 배치를 단계별로 구분하고 동적 생성 뒤 최하위에서 최상위 순서로 레이아웃을 갱신한다.

### 2026-08-21 제작 화면 최초 진입 패널 표시 누락

* 증상: 최초 작업에서는 Play 씬에서 제작 화면에 처음 진입하면 제작 패널이 보이지 않았고 화면을 여러 번 전환한 뒤에야 나타났다. 2026-08-25 UI 교체 검증에서는 시작 시 비활성인 상점 / 사이드 액션이 초기화 전에 호출됐고 제작 버튼 첫 입력에서는 비활성 제작 본체 아래의 파츠 선택 패널이 위치 기준을 저장하기 전에 사용되어 Null 오류가 발생했다.
* 원인: `PlayScene`의 실행 순서를 일반 뷰보다 뒤로 두어도 비활성 부모 아래의 뷰는 활성화 전까지 `Awake`가 실행되지 않는다. 외부 초기화 / 표시 함수가 비활성 자식 뷰의 `Awake`에서 준비할 런타임 필드를 먼저 사용한 것이 공통 원인이다.
* 해결: 상점 / 인벤토리 / 주문 / 제작 목록 / 정비 / 사이드 액션과 제작 사이드 패널의 외부 호출 필수값을 명시적 `InitializeRuntime`에서 준비하고 각 프레젠터 초기화 시작 시 먼저 호출하도록 통일했다.
* 확인: 상점 / 사이드 액션의 최초 초기화 오류가 사라졌고 제작 버튼 첫 입력에서 제작 목록과 사이드 패널이 정상 표시되는 것을 사용자 Play Mode에서 확인했다.
* 재발 방지: 비활성 가능성이 있는 뷰의 외부 호출 필수값을 `Awake`에만 두지 않는다. 프레젠터 초기화 중 접근할 뷰는 명시적 초기화를 먼저 호출하고 새 UI 연결 전 [TODO.md](TODO.md)의 `BEFORE_UI_REWORK` 1번 기준과 이 오류 기록을 확인한다.

### 2026-08-25 공용 풀·동적 View 종료 정리 순서

* 증상: 주문 / 상점 / 정비 / 직원 슬롯이나 튜토리얼 강조 대상이 활성화된 상태에서 Play Mode를 종료하면 부모 View의 `OnDisable`이 이미 파괴된 자식이나 타깃을 반환·복구하면서 `MissingReferenceException`이 발생했다.
* 원인: 씬 계층의 부모 View와 자식 슬롯·강조 대상은 종료 시 비활성화 / 파괴 호출 순서가 보장되지 않는다. C# 참조가 남아 있어도 Unity Object는 먼저 파괴될 수 있으므로 `OnDisable`만으로 대상 생존을 보장할 수 없다.
* 해결: `Poolable`의 대여 상태와 `PoolManager`의 실행 종료 전 일괄 반환으로 중복 반환을 차단하고, View별 슬롯 정리와 강조 복구는 파괴된 Unity Object를 건너뛰도록 통일했다. Play 씬 재시작과 타이틀 이동도 씬 전환 전에 활성 슬롯을 먼저 반환한다.
* 확인: 주문 / 상점 / 튜토리얼의 대표 종료 오류는 제거했다. 직원 슬롯 방어 코드는 적용했으며 정비 고용 화면을 연 상태의 Play Mode 종료를 추가 확인한다.
* 재발 방지: `OnDisable` / `OnDestroy`에서 동적 자식의 컴포넌트·Transform·GameObject에 접근하기 전에 Unity null을 검사하고, 살아 있는 대상만 Tween 복구와 풀 반환을 수행한다.

### 2026-07-30 비활성 UI의 Awake / Init 실행 순서

* 증상: 동적으로 생성한 일반 주문 슬롯이 검정 투명하게 표시되고 선택 상태의 Outline도 활성화됐지만 보이지 않았다.
* 원인: 비활성 부모 아래에 생성된 View는 Awake보다 외부 Init 호출이 먼저 실행될 수 있는데, Awake에서 저장할 예정이던 일반 색상을 Init에서 사용해 Color 기본값인 검정 투명이 적용됐다.
* 영향: 투명해진 Image와 Use Graphic Alpha를 사용하는 Outline의 알파가 함께 0이 되어 슬롯 배경과 외곽선이 모두 보이지 않았다.
* 해결: 외부 Init에 필요한 초기값은 Awake 실행을 전제로 하지 않고 Init 내부에서 먼저 저장하도록 변경했다.
* 확인: 일반 주문 슬롯의 기본 색상과 주문·제작 목록의 선택 Outline 표시가 정상 동작했다.

### 2026-07-30 배치 파츠 재선택과 스케일 입력 범위 오류

#### 발생 배경

* 제작 화면에서 슬롯으로 생성한 파츠와 이미 배치된 파츠가 같은 선택 / 드래그 / 스케일 변경 흐름을 사용하도록 PC 기본 입력을 연결하던 중 발생했다.
* 선택 상태의 단일 원본은 CraftPresenter의 배치 번호이며 PartsView의 선택 여부는 외곽선 표시와 입력 제한에 사용하는 View 상태이다.
* 파츠 생성 직후에는 CraftPresenter가 새 배치 번호를 직접 선택하지만 기존 파츠의 재선택은 PartsView의 Pointer 입력을 거치므로 두 진입 경로의 실행 시점이 달랐다.

#### 기대 동작

* 슬롯에서 파츠를 생성하거나 기존 파츠를 클릭하면 해당 파츠가 즉시 선택되어야 한다.
* 빈 제작 영역을 클릭하기 전까지 선택을 유지하고 선택 파츠 자신의 영역 위에서 휠을 굴리면 스케일을 0.1씩 변경해야 한다.
* 클릭을 유지한 상태에서도 드래그 이동과 휠 스케일 변경이 각각 입력되어야 하며 다른 파츠의 상태에 영향을 주면 안 된다.

#### 증상과 재현

* 슬롯에서 새로 생성되어 즉시 선택된 파츠는 정상적으로 스케일을 변경할 수 있었다.
* 빈 영역 클릭으로 선택을 해제한 뒤 같은 파츠를 재선택하면 휠 입력이 동작하지 않았다.
* 재선택하려고 클릭을 유지하면 위치만 이동하고 스케일은 변경되지 않았다.
* 재선택 상태에서도 커서가 몸통 근처에 있을 때만 스케일이 변경되는 것처럼 보여 선택 상태 / 드래그 상태 / 커서 위치가 서로 다른 원인 후보가 되었다.
* 생성 직후에는 정상이라는 점에서 CraftModel의 스케일 계산과 PartsView 표시 갱신보다 생성과 재선택의 입력 경로 차이를 우선 확인했다.

#### 입력 흐름 확인

* 정상 흐름은 PartsView 입력 -> CraftView 중계 -> CraftPresenter의 선택 배치 번호 확인 -> CraftModel 상태 변경 -> 해당 PartsView 갱신 순서이다.
* 생성 직후에는 CraftPresenter가 SelectPlacedPart를 직접 호출해 Pointer 입력 없이 선택 상태가 만들어졌다.
* 재선택은 파츠 Pointer 입력과 부모 BabyBuildArea의 빈 영역 Button 입력이 같은 클릭에서 함께 처리될 가능성이 있었다.
* 스케일 입력은 선택 번호 / 루트 몸통 여부 / 휠 방향 / 커서 위치 검사를 차례로 통과해야 해 어느 단계에서 종료되는지 증상별로 나누어 확인했다.

#### 중간 확인과 실패한 접근

* 처음에는 한 파츠가 최소·최대 스케일에 도달한 뒤 공용 상태가 다른 파츠까지 막는 것으로 의심했으나 생성 직후 다른 파츠는 정상 동작해 스케일값 공유 문제를 제외했다.
* 드래그 종료 이벤트 누락으로 CraftPresenter의 드래그 번호가 남는 경우를 확인하고 선택 전환과 패널 이동 시 초기화했지만 재선택 직후의 입력 실패는 계속됐다.
* 파츠 클릭이 부모 빈 영역 선택으로 전달되는 문제를 막기 위해 선택을 PointerClick으로 옮겼으나 선택이 마우스 버튼을 뗀 뒤에 확정되어 클릭 유지 중에는 여전히 선택되지 않았다.
* 클릭 유지 중 드래그와 스케일의 충돌을 피하려고 왼쪽 버튼을 누르는 동안 휠을 차단했으나 사용자가 실제로 사용하는 클릭 유지 + 휠 조작까지 차단했다.
* EventSystem 전달 문제를 피하려고 Mouse.current.position으로 제작 영역을 직접 판정했으나 Editor Game View와 UI 좌표 기준이 어긋나 중앙의 일부 영역에서만 입력이 통과했다.
* 각 중간 수정은 한 증상만 해결하거나 새로운 입력 조건을 추가했기 때문에 생성 -> 선택 해제 -> 재선택 전체 절차를 다시 검증했을 때 실패했다.

#### 최종 원인

* 생성 직후 선택은 즉시 확정되지만 재선택은 PointerClick 시점까지 지연되어 같은 기능의 선택 시점이 일치하지 않았다.
* 자식 PartsView가 클릭 완료 입력을 처리하지 않아 같은 클릭이 부모 BabyBuildArea의 빈 영역 Button까지 전달되고 방금 선택한 파츠가 다시 해제될 수 있었다.
* 왼쪽 버튼 입력 차단이 드래그만 구분하지 않고 클릭 유지 상태의 모든 휠 입력을 함께 차단했다.
* UI EventSystem이 보정한 Pointer 좌표 대신 마우스 위치를 직접 사용하면서 파츠 입력 영역과 커서 좌표 판정이 일치하지 않았다.
* 전체 제작 영역에서 현재 선택 파츠를 변경하는 입력과 개별 파츠가 자기 입력을 전달하는 책임이 혼재해 증상과 실제 입력 대상이 달라졌다.

#### 해결 방법

* PartsView의 OnPointerDown에서 배치 번호를 즉시 전달해 생성 직후와 재선택의 선택 확정 시점을 맞췄다.
* PartsView가 IPointerClickHandler를 구현해 파츠 클릭 완료 입력을 소비하고 부모 BabyBuildArea의 빈 영역 선택 처리로 전달되지 않게 했다.
* 왼쪽 버튼을 누르는 동안 휠을 일괄 차단하던 조건을 제거해 클릭 유지 상태에서도 스케일 입력을 받을 수 있게 했다.
* 전체 BabyBuildArea의 Mouse.current 위치 판정을 제거하고 선택된 PartsView가 자기 영역의 IScrollHandler로 휠 입력을 직접 받도록 변경했다.
* PartsView는 배치 번호와 휠 방향을 CraftView에 전달하고 CraftPresenter는 전달된 번호와 현재 선택 번호가 일치할 때만 CraftModel과 해당 View의 스케일을 변경한다.
* 파츠별 입력이 배치 번호를 포함하므로 다른 파츠 또는 몸통 영역 위의 휠이 현재 선택 파츠를 변경하지 않는다.

#### 검증

* 파츠 생성 직후 선택과 휠 스케일 변경을 확인했다.
* 빈 영역 선택 해제 -> 기존 파츠 클릭 재선택 -> 클릭 유지 -> 휠 스케일 변경 순서를 확인했다.
* 재선택 파츠의 위치 이동과 스케일 변경이 함께 동작하는지 확인했다.
* 선택된 파츠 자신의 영역 위에서만 스케일이 변경되고 몸통 / 빈 영역 / 다른 파츠 영역의 휠은 영향을 주지 않는지 확인했다.
* 한 파츠가 최소·최대 스케일에 도달한 뒤 다른 파츠를 선택해 독립적으로 스케일을 변경할 수 있는지 확인했다.

#### 재발 방지와 배운 점

* UI Pointer 입력은 Mouse.current의 직접 좌표보다 EventSystem이 전달한 PointerEventData를 우선 사용한다.
* 생성 직후처럼 코드가 직접 만든 상태와 사용자가 다시 선택해 만든 상태를 같은 기능으로 보지 않고 각각 검증한다.
* 자식 View의 입력만 확인하지 않고 부모 Button / Scroll View까지 이벤트가 전달되는지 함께 확인한다.
* 입력 이벤트에는 대상 배치 번호를 포함하고 Presenter가 현재 선택과 다시 대조해 다른 파츠 상태 변경을 막는다.
* 컴파일 성공이나 최초 1회 동작만으로 입력 구현을 완료 처리하지 않고 선택 해제 / 재선택 / 드래그 / 경계값 / 다른 대상 전환까지 전체 재현 절차를 반복한다.
* 증상 하나에 원인 하나만 있다고 단정하지 않고 선택 상태 / 입력 시점 / 이벤트 전달 / 좌표계 / Model 결과 / View 반영 단계를 분리해 확인한다.

### 2026-08-04 결산 Content 전환 시 스크롤 위치 계승 오류

#### 증상

* 결산을 처음 표시하면 Scroll View가 최상단이 아니라 최하단에서 시작했다.
* 일일 결산을 아래로 내린 뒤 주간 결산으로 전환하면 일일 결산의 마지막 스크롤 위치가 주간 결산에 그대로 적용됐다.
* 같은 결산을 표시한 상태에서 다시 검증 요청을 실행하면 두 번째 표시부터 최상단으로 이동했다.

#### 원인

* 하나의 ScrollRect에서 `DailyContent`와 `WeeklyContent`를 교체하면서 ScrollRect의 기존 위치와 이동 상태가 함께 유지됐다.
* 새 Content를 연결한 직후에는 TMP 텍스트와 레이아웃의 최종 높이가 확정되지 않아 `verticalNormalizedPosition = 1f`가 이전 Content 높이를 기준으로 적용되거나 무시됐다.
* Content 교체 이후에만 위치를 초기화해 이미 유효한 일일 Content의 스크롤 상태를 제거하지 못했다.

#### 해결 과정

* RectTransform 피벗 변경만으로는 ScrollRect가 보관한 위치가 초기화되지 않아 증상이 유지됐다.
* 한 프레임 대기 후 레이아웃을 강제 갱신하고 최상단으로 이동해 최초 일일 결산은 해결했지만 일일 결산에서 주간 결산으로 전환할 때는 이전 위치가 계속 계승됐다.
* 렌더링 완료 후 최상단 위치를 다시 확정해도 Content 교체 전에 남은 일일 스크롤 상태까지 제거하지는 못했다.

#### 최종 해결

* Content를 교체하기 전에 현재 ScrollRect의 이동을 중단하고 기존 Content가 유효한 상태에서 최상단으로 초기화했다.
* 새 Content 연결 후 TMP와 Content Size Fitter의 레이아웃 계산이 끝날 때까지 기다렸다.
* 최종 Content 크기를 반영한 뒤 ScrollRect 이동을 다시 중단하고 최상단 위치를 재확정했다.

#### 확인

* ContextMenu 검증으로 처음 표시한 일일 결산이 최상단에서 시작하는 것을 확인했다.
* 일일 결산을 아래로 내린 뒤 주간 결산으로 전환해도 주간 결산이 최상단에서 시작하는 것을 확인했다.
* 사용자 Play Mode 확인을 완료했다.

#### 재발 방지

* 같은 ScrollRect에서 Content를 교체할 때는 새 Content의 위치만 초기화하지 않고 기존 Content가 유효할 때 이전 스크롤 상태부터 제거한다.
* TMP와 자동 레이아웃을 사용하는 동적 Content는 활성화 직후의 RectTransform 높이를 최종값으로 보지 않는다.
* 최초 표시와 Content 간 전환을 별도 경로로 검증하고 이전 페이지를 스크롤한 상태에서도 새 페이지의 초기 위치를 확인한다.
