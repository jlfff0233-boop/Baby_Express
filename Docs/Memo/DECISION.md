# DECISION

## PURPOSE

프로젝트 전체에 공통 적용되는 확정 기획 / 구조 / 범위와 시스템 문서 색인을 관리한다.

* 시스템별 상세 규칙 / 예시 / 미결정 사항은 System 폴더의 담당 파일을 단일 원본으로 사용한다.
* 실제 구현 완료 상태는 [DONE.md](DONE.md) / 현재 작업과 시스템 간 선행 작업은 [TODO.md](TODO.md) / 진행 차단 오류는 [ERROR.md](ERROR.md)에서 관리한다.
* 이 파일과 시스템 문서에 같은 상세 내용을 중복 기록하지 않는다.

## CURRENT_DECISION

프로젝트 공통 방향

* 프로젝트명은 Baby Express이다.
* 장르는 2D 타이쿤 / 경영 / 제작 시뮬레이션이다.
* 플랫폼은 PC / 모바일이며 Unity 6 6000.0.68f1을 사용한다.
* 개발 기간은 약 1.5~2개월이며 Unity 프로그래머 서브 포트폴리오 제작을 목표로 한다.
* 핵심 게임 루프는 예산 지급 -> 발주 -> 주문 확인 -> 악마 아기 제작 -> 배송 -> 평가 -> 수익 -> 정비 -> 다음 영업일이다.
* 새로운 기능보다 기존 Model / Presenter / 데이터 구조 재사용을 우선하고 구현 기간 안에서 MVP를 먼저 완성한다.
* 동일한 재미를 더 적은 구현 비용으로 만들 수 있으면 축소안을 우선 검토한다.

### 게임 콘셉트

* 황새들이 보험 문제로 위험 지역인 지옥의 아기 배송을 기피해 지옥이 저출산·초고령 사회가 되었다.
* 플레이어는 Baby Express를 창업하고 마녀에게 악마 아기 파츠를 발주해 부모 악마의 주문에 맞는 아기를 제작하고 배송한다.
* 핵심 재미는 한정된 예산과 재고 안에서 주문 조건 / 제작 코스트 / 파츠 시너지를 함께 고려해 결과를 최적화하는 것이다.

### 메인 화면 구성

* 메인 버튼은 주문 / 상점 / 인벤토리 / 제작 / 정비로 구성한다.
* 서브 버튼은 가계부 / 카탈로그 / 업적 / 설정으로 구성한다.
* 정비 화면은 관리 / 시설 / 연구 / 편의 / 고용 탭으로 구성하며, 관리는 전체 현황을 모아보는 화면이고 시설 / 연구 / 편의 / 직원이 실제 성장 대상이다.
* 가계부는 영업 종료 시 표시되는 결산 실행 화면과 구분하며 과거 주간 결산을 모아보는 읽기 전용 화면이다.
* 사이드 액션의 공통 중재자는 가계부 / 카탈로그 / 업적 / 설정의 진입과 닫기, 한 번에 하나의 화면만 표시되는 상태를 관리한다.
* 각 사이드 액션 Presenter는 담당 View 입력과 표시만 소유하며 다른 사이드 액션의 View를 직접 갱신하지 않는다.
* 사이드 액션 화면을 열 때 담당 Presenter가 현재 Model 상태를 다시 조회하고, 닫을 때 메인 화면 상태를 변경하거나 날짜 진행을 호출하지 않는다.
* 메인 시스템 화면 / 결산 / 파산 화면이 열려 있는 동안 사이드 액션 버튼을 숨기고 메인 화면으로 돌아오거나 다음 영업일을 시작하면 다시 표시한다.
* 설정은 타이틀과 플레이 화면에서 같은 값을 사용하며 실제 적용값과 UI 편집 중인 임시값을 구분한다.
* 타이틀 1차는 새 게임 / 이어하기 / 설정 / 종료로 구성하고 엔딩 1차는 총 결산 / 이번 주부터 다시 시작 / 처음부터 다시 시작 / 시작 화면 복귀로 구성한다.

### UI 표시와 연출

* 기존 기능 배치는 유지하되 텍스트만 배치된 정보 패널에는 아이콘 / 대표 이미지 / 상태 이미지를 함께 표시하고, 텍스트 비중이 특히 높은 결산 화면을 우선 재구성한다.
* 공용 패널은 중심의 작은 크기에서 원래 크기로 빠르게 펼쳐지고 살짝 튕기며 나타난다. 닫을 때는 반대 순서로 중심을 향해 수축한 뒤 비활성화한다.
* 버튼은 기본 상태에서 반복해서 깜빡이거나 반짝이지 않는다. 클릭할 때만 짧게 눌렸다가 튕겨 돌아오는 연출을 사용하고, Shader Graph 광택 이동은 특수 버튼 효과가 필요한 경우에만 후순위로 검토한다.
* 날짜 / 시간 / 자금 / 일일 제작 할당량은 실제 값이 변경될 때 표시 연출을 적용한다. 저장 복구 / 화면 초기화 / 단순 재표시 때는 연출과 효과음 없이 최종값을 즉시 표시한다.
* 자금 수입은 코인 아이콘이 튀어 오르며 반짝인 뒤 자금 표시로 이동하고 숫자가 증가하는 흐름으로 표현한다. 지출은 코인 아이콘이 자금 표시에서 빠져나간 뒤 숫자가 감소하는 흐름으로 표현하며, 연출 완료 시 실제 최종 자금과 정확히 일치해야 한다.
* 수입 연출에는 코인 도착 시 짧은 자금 강조와 띠링 계열 효과음을 사용하고, 연속 변경은 이전 Tween을 정리한 뒤 최종값을 기준으로 갱신한다.
* 튜토리얼 화살표 / 신규 알림 / 파츠 배치 피드백은 공용 강조 연출을 재사용한다. 위치 반복 이동은 튜토리얼 화살표에만 사용하고, 신규 알림은 버튼이 아니라 알림 아이콘만 깜빡이며, 파츠는 생성·이동·크기 조절을 끝낸 시점에만 짧게 탄성 강조한다.
* 튜토리얼 행동 대상은 처음 한 번만 크기를 강조한 뒤 원래 상태로 복구하고 이후에는 화살표만 이동과 깜빡임을 반복한다. 풀링 주문 / 상품 / 아이템 슬롯은 Inspector의 고정 오브젝트를 참조하지 않고 담당 ID로 현재 활성 슬롯을 조회해 런타임에 연결한다.
* 버튼 Shader Graph는 기본 범위에서 사용하지 않고 스프라이트 / Animation / DOTween으로 부족한 특수 버튼 효과가 확정될 때만 후순위로 검토한다.
* 홈 화면은 Baby Express 팩토리 내부를 기본으로 하며 성장에 따라 배송 상자 / 선반 / 제작 장비 / 직원 / 배송 준비 공간이 추가되는 구조를 사용한다. 가능한 항목은 실제 정비 진행 상태와 연결해 가게 성장도를 시각적으로 보여준다.
* 플레이어 캐릭터 외형을 홈 화면의 필수 요소로 두지 않으며, 튜토리얼 캐릭터 이미지는 대화와 행동 유도 연출에서 우선 사용한다.
* 기본 배경과 움직이는 장식 배경은 별도 레이어로 구성한다. 기본 배경은 고정하고 반복 경계가 이어지지 않는 장식 이미지는 UV 반복보다 화면 위치 이동을 우선 사용한다.
* 음원 참조의 단일 원본은 `AudioClipMap`으로 두고 `AudioManager`는 오디오 소스 / 믹서 / 현재 장면과 이벤트 BGM 상태 / 재생 요청만 관리한다.
* 순수 UI 반응음은 공용 View 연출에서 재생하고 구매 / 판매 / 제작 / 배송 / 주문 / 업적처럼 처리 결과가 있는 효과음은 성공 또는 실패가 확정된 중재 흐름에서 요청하며 Model은 오디오를 참조하지 않는다.

## MVP_PATTERN

모든 시스템 공통 책임 분리

* 모든 시스템은 Model / View / Presenter 역할을 분리한다.
* Model은 데이터 / 계산 / 검증 / 게임 규칙 / 게임 규칙 실패 처리를 담당하고 UI를 참조하지 않는다.
* View는 표시 / 플레이어 입력 / 입력 이벤트 전달만 담당하고 Model을 직접 참조하거나 규칙을 판단하지 않는다.
* Presenter는 View 이벤트 구독 / Model 호출 순서 / ViewData 변환 / 담당 View 갱신을 중재하고 계산을 직접 구현하지 않는다.
* Presenter는 자신이 담당하는 View만 갱신하고 다른 Presenter의 View를 직접 참조하지 않는다.
* 여러 Model을 변경하는 처리는 변경 전 전체 사전 검증을 수행하고 실패 시 부분 상태 변경을 남기지 않는다.
* PlayScene은 공용 Model 생성 / Presenter 의존성 연결 / 씬 생명주기를 담당하고 게임 규칙을 직접 처리하지 않는다.
* PlayStateModel은 날짜와 자금 등 공통 플레이 상태를 관리하며 작은 Model로 과도하게 분리하지 않는다.
* TopBar는 PlayStateModel 변경 이벤트를 구독하는 TopBarPresenter가 갱신한다.

## TERMINOLOGY

프로젝트 공통 용어

* Shop은 상품 목록 / 필터 / 장바구니 / 구매 확정을 포함한 전체 상점 화면과 흐름이다.
* Purchase는 장바구니 / 자금 / 상점 재고 / 인벤토리를 검증하고 최종 상태를 변경하는 구매 처리이다.
* 상점에서 판매 중인 대상은 상품 / 인벤토리에 보유한 대상은 아이템으로 표현한다.
* 상점의 `시설`은 배치 가능한 장비 / 가구 / 시설 확장 상품군이며, 정비의 `시설`은 상점·제작·주문·배송 등의 수치 성장 분류이므로 서로 같은 의미로 사용하지 않는다.
* 정비 상품의 상점 분류와 정비 분류는 독립적이며 상점에서는 `ProductType` / 정비 화면에서는 `MaintenanceType`을 기준으로 구분한다.
* 주문 조건은 최소 제작 조건 / 주요 요구 사항 / 희망 사항 / 시너지로 구분한다.
* 주문 진행 상태 / 기한 상태 / 최종 결과는 서로 다른 정보로 관리한다.
* 화면 표시 명칭 `정비`는 시설 개선 / 해금 / 직원 고용과 관리를 포함한다.

## SYSTEM_BOUNDARY

시스템 간 상세 규칙 소유권

* 재입고 수량과 간격 계산은 SHOP / 다음 날 재입고 호출 시점은 DAY가 담당한다.
* 주문 조건 원본과 주문 상태는 ORDER / 제작물의 조건·테마 판정은 CRAFT가 담당한다.
* 판정 결과의 점수 / 등급 / 배송 보정 / 보상은 DELIVERY가 담당한다.
* 직원이 제공하는 효과와 자동화 허용 범위는 UPGRADE / 효과가 적용되는 실제 계산은 담당 시스템이 처리한다.
* 카탈로그는 기존 시스템 데이터를 읽기만 하고 구매 / 장착 / 제작 계산 책임을 갖지 않는다.
* 시스템 파일 사이에는 상세 규칙을 복사하지 않고 담당 파일을 참조한다.

* System 파일의 PENDING과 [TODO.md](TODO.md)는 미구현 또는 미확정 항목이며 확정 규칙으로 해석하지 않는다.
* DECISION / System / DONE / 현재 코드 / 사용자 설명이 충돌하면 임의로 선택하지 않고 사용자에게 확인한다.

## UPDATE_RULE

전역 규칙이나 시스템 경계가 변경될 때만 이 파일을 갱신하고 시스템 상세 변경은 담당 System 파일에 기록한다.
